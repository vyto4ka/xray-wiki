На роутерах, Linux-десктопах и серверах Xray тесно взаимодействует с ядром операционной системы. Эти четыре механизма чаще всего встречаются в разделах про прозрачный прокси, `sockopt` и производительность `XTLS`.

## TUN, TPROXY и REDIRECT {#tun-tproxy-redirect}

Обычный прокси (:term[socks]{SOCKS5} или HTTP) требует указывать адрес прокси в настройках каждой программы. Чтобы заворачивать в Xray трафик **всей системы** (включая игры и системные службы), применяют один из трёх подходов:

| Механизм | Уровень работы | Плюсы и особенности |
| :--- | :--- | :--- |
| **TUN** (`protocol: "tun"`) | L3 (виртуальная сетевая карта) | Работает на Linux, Windows, macOS, Android и iOS. Перехватывает TCP и UDP целиком, но требует обработки IP-пакетов в пространстве пользователя (userspace). |
| **TPROXY** (`sockopt.tproxy: "tproxy"`) | Ядро Linux (`nftables` / `iptables`) | Прозрачно перехватывает **и TCP, и UDP** без создания виртуальной карты TUN и без подмены адреса назначения. Лучший выбор для Linux-роутеров (OpenWrt). |
| **REDIRECT** (`sockopt.tproxy: "redirect"`) | Ядро Linux (NAT) | Работает только для **TCP** (переписывает адрес назначения на локальный порт Xray). Проще настраивается, но не умеет перехватывать UDP. |

## Метка пакетов fwmark (SO_MARK) {#fwmark}

Когда вы включаете прозрачный прокси (TPROXY/REDIRECT) на роутере, возникает риск **сетевой петли**: Xray перехватывает пакет браузера, шифрует его и отправляет в интернет, но правило файрвола снова перехватывает уже исходящий пакет самого Xray и возвращает его обратно в Xray.

Чтобы разорвать петлю, Xray помечает все свои исходящие сокеты числовой меткой ядра Linux **`SO_MARK` (`fwmark`)** через параметр `sockopt.mark` (например, `255`). В `nftables` или `iptables` добавляется первое правило: "пакеты с меткой `255` не трогать и выпускать напрямую в интернет".

## ReadV и zero-copy Linux splice() {#readv-splice}

При обычной пересылке данных через прокси каждый байт проходит длинный путь с копированием памяти:

`Сетевая карта → буфер ядра Linux → память процесса Xray (userspace) → снова буфер ядра → сетевая карта`

Xray-core использует две оптимизации, резко снижающие нагрузку на процессор:

- **ReadV:** векторизованное чтение из сокета сразу в несколько буферов памяти за один системный вызов.
- **Linux `splice()` (Zero-Copy):** системный вызов ядра Linux, который напрямую перекладывает данные из одного TCP-сокета в другой **внутри ядра**, вообще не копируя их в память Xray.

:::tip Когда включается `splice()` и почему "замирает" счётчик скорости
В режиме **XTLS Vision** (`xtls-rprx-vision`) на Linux/Android ядро Xray автоматически передаёт соединение в `splice()`, как только видит внутри чистый TLS 1.3 и совместимый TCP-транспорт (`raw`). Пока соединение обслуживается напрямую ядром, Xray не видит объём проходящих байтов в реальном времени — статистика по такому соединению обновляется в момент его закрытия.
:::
