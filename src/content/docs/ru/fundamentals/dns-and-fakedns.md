Прежде чем браузер откроет `example.com`, операционная система должна узнать его IP-адрес. За это отвечает **DNS** (Domain Name System). В Xray правильная настройка DNS напрямую влияет на точность маршрутизации, скорость открытия сайтов и отсутствие утечек.

## Как работает DNS и какие записи бывают {#how-dns-works}

Приложение отправляет DNS-резолверу запрос с именем домена и типом нужной записи:

| Тип записи | Что возвращает | Зачем нужна в Xray |
| :--- | :--- | :--- |
| `A` | IPv4-адрес домена | Обычное подключение по IPv4 |
| `AAAA` | IPv6-адрес домена | Подключение по IPv6 (влияет на `queryStrategy`) |
| `CNAME` | Псевдоним другого домена | Привязка поддоменов к CDN |
| `HTTPS` / `SVCB` | Параметры HTTP/3 и ключи :term[ech] | Необходимы для автоматического получения `echConfigList` |
| `SRV` / `TXT` | Динамический адрес и порт сервиса | Используется в `sockopt.addressPortStrategy` |

## Шифрованный DNS: DoH, DoT и DoQ {#encrypted-dns}

Классический DNS работает по открытому :term[udp]{UDP} на порту 53. Провайдер может свободно читать все запрашиваемые домены и подменять ответы (**DNS Poisoning / Spoofing**), возвращая вместо реального IP-адреса заглушку.

Чтобы защитить запросы, применяются шифрованные транспорты:

- **DoH (DNS over HTTPS)**: DNS-запросы внутри обычного HTTPS (`https://1.1.1.1/dns-query`). В Xray префикс `https+local://` отправляет запрос напрямую в сеть, а `https://` — через маршрутизатор Xray (внутрь прокси).
- **DoT (DNS over TLS)**: DNS поверх выделенного TLS-соединения (порт 853).
- **DoQ (DNS over QUIC)**: DNS поверх :term[quic] (`quic+local://dns.adguard-dns.com`), быстрый и устойчивый к потерям пакетов.

## EDNS Client Subnet (ECS) {#ecs}

Крупные сайты и :term[cdn] возвращают разные IP-адреса в зависимости от того, из какой страны пришёл DNS-запрос. Если вы делаете DNS-запрос через зарубежный прокси, сайт может выдать сервер на другом континенте.

Расширение **EDNS Client Subnet (ECS)** (поле `clientIp` в конфиге DNS Xray) передаёт DNS-серверу ваш префикс подсети (без точного адреса устройства), чтобы CDN выбрал географически ближайший узел.

## Утечки DNS и принцип работы FakeDNS {#fakedns-concept}

**Утечка DNS (DNS Leak)** происходит, когда сам трафик идёт через прокси, но DNS-запрос к заблокированному сайту уходит в открытый DNS провайдера.

В прозрачных прокси (:term[tun], :term[tproxy]) есть ещё одна проблема: приложение сначала делает DNS-запрос, получает реальный IP и открывает соединение уже **по IP-адресу**. Без анализа содержимого прокси не знает, к какому домену изначально обращалась программа, и не может применить доменные правила маршрутизации (`geosite:`).

**FakeDNS** решает обе задачи сразу:

1. Приложение спрашивает у Xray IP для `example.com`.
2. Вместо ожидания внешнего DNS-ответа Xray мгновенно выдаёт **фиктивный IP** из служебного пула (по умолчанию `198.18.0.0/15` для IPv4 и `fc00::/18` для IPv6) и запоминает соответствие в таблице в памяти.
3. Приложение открывает соединение к `198.18.0.12`.
4. Модуль **Sniffing** (`destOverride: ["fakedns"]`) подменяет фиктивный IP обратно на `example.com`, правила маршрутизации срабатывают по точному домену, а реальное разрешение имени происходит уже на стороне удалённого сервера.

:::warning Обязательное условие для FakeDNS
FakeDNS работает корректно только при включённом `sniffing` с `fakedns` в `destOverride` на соответствующем `inbound`. Без этого фиктивные адреса `198.18.x.x` уйдут в сеть и соединение оборвётся.
:::
