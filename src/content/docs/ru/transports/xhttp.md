**XHTTP** (ранее *SplitHTTP*) — собственный HTTP-транспорт Xray-core, объединяющий возможности старых транспортов (`WS`, `HTTPUpgrade`, `gRPC`, `H2`, `QUIC`). Он работает поверх **HTTP/1.1**, **HTTP/2** и **HTTP/3 (:term[quic])**, проходит через :term[cdn] и веб-серверы (Nginx, Caddy), сочетается с **REALITY** и **VLESS Encryption**, а также поддерживает **разделение восходящего и нисходящего каналов**.

:::tip Как проверить фактический режим работы XHTTP
Установите `log.loglevel: "info"` на клиенте. При подключении Xray запишет в журнал реальную версию HTTP (`h1`/`h2`/`h3`), заголовок `Host`, выбранный режим (`packet-up` / `stream-up` / `stream-one`) и статус разделения каналов.
:::

## Четыре режима работы (`mode`) {#xhttp-modes} :orig[~:STREAM-UP/ONE | XHTTP 传输模式]

| Режим `mode` | Как устроен обмен | Когда выбирать |
| :--- | :--- | :--- |
| **`auto`** *(по умолчанию)* | **Клиент:** выбирает `stream-up` при TLS H2, `stream-one` при REALITY (если не задан `downloadSettings`), иначе `packet-up`. **Сервер:** принимает все три режима одновременно. | Оптимальный выбор в 95% случаев, не требует ручного подбора. |
| **`packet-up`** | Вверх (uplink) идут отдельные короткие `POST /path/<uuid>/<seq>`, а вниз (downlink) открывается потоковый `GET /path/<uuid>` с :term[sse]. | Самый совместимый режим: проходит через CDN, которые буферизуют тело `POST`, и работает по HTTP/3. |
| **`stream-up`** | Вверх идёт потоковый `POST /path/<uuid>` (с заголовком :term[grpc]), вниз идёт потоковый `GET /path/<uuid>`. | Высокая скорость отдачи через Cloudflare (при включённой опции gRPC в панели CF) и Nginx (`grpc_pass`). |
| **`stream-one`** | Один двунаправленный поток внутри единственного `POST /path/`. | Минимум служебных запросов для прямого `XHTTP + REALITY` без разделения каналов. |

## Как выбирается версия HTTP (H1 / H2 / H3) {#http-version-selection} :orig[~:对于 XHTTP 客户端 | HTTP 版本选择]

- **Сервер XHTTP** по умолчанию слушает TCP и обслуживает HTTP/1.1 и HTTP/2. Чтобы принимать HTTP/3 (QUIC), лучше поставить перед Xray настоящий **Nginx / Caddy** или **CDN** (они примут H3 от клиента и перешлют H2 на Xray).
- **Клиент XHTTP:**
  1. При включённом `TLS` или `REALITY` по умолчанию используется **HTTP/2 (`h2`)**, без них работает `HTTP/1.1`.
  2. Если в `tlsSettings.alpn` оставить только `["http/1.1"]`, клиент переходит на `HTTP/1.1`.
  3. Если в `tlsSettings.alpn` оставить только `["h3"]`, клиент использует **HTTP/3 (quic-go)**.

## Базовые поля и контейнер `extra` {#xhttp-config} :orig[~:downloadSettings | XHTTP 完整配置]

```jsonc
"xhttpSettings": {
  "host": "example.com",
  "path": "/yourpath",
  "mode": "auto",
  "extra": {
    "headers": {},
    "xPaddingBytes": "100-1000",
    "noGRPCHeader": false,
    "noSSEHeader": false,
    "scMaxEachPostBytes": 1000000,
    "scMinPostsIntervalMs": 30,
    "scMaxBufferedPosts": 30,
    "scStreamUpServerSecs": "20-80",
    "xmux": {
      "maxConcurrency": "16-32",
      "maxConnections": 0,
      "cMaxReuseTimes": 0,
      "hMaxRequestTimes": "600-900",
      "hMaxReusableSecs": "1800-3000",
      "hKeepAlivePeriod": 0
    },
    "downloadSettings": {}
  }
}
```

- **`host`**: значение HTTP-заголовка `Host`. На клиенте действует приоритет `host > serverName > address`. Если указать `host` на сервере, Xray будет отклонять запросы с другим `Host` (если не нужна строгая проверка, на сервере поле обычно оставляют пустым). Не дублируйте `Host` внутри `headers`. :orig[~:host 的行为 | host 优先级]
- **`path`**: URL-путь (например, `"/yourpath"`). Должен точно совпадать на сервере, клиенте и в `downloadSettings`. В режиме `stream-one` завершающий слэш `/` добавляется автоматически. :orig[~:path | path 路径]
- **`mode`**: `"auto"` | `"packet-up"` | `"stream-up"` | `"stream-one"`. На сервере указание конкретного режима запрещает остальные (исключение: `"stream-up"` на сервере также принимает `"stream-one"`). :orig[~:mode | mode 模式]
- **`extra`**: JSON-контейнер для всех расширенных параметров. Если объект `extra` присутствует, Xray читает все тонкие настройки именно из него, а в ссылках `vless://` весь объект передаётся одним параметром `extra`. :orig[~:extra 是 | extra 字段说明]

## Мультиплексор XMUX (`extra.xmux`) {#xmux} :orig[~:XMUX | XMUX 多路复用]

В HTTP/2 и HTTP/3 встроен мультиплексор **XMUX** (:term[multiplexing]). Он позволяет новым прокси-запросам стартовать за **0-:term[rtt]** внутри уже открытых соединений и автоматически переоткрывает базовые TCP/QUIC-каналы до того, как их оборвёт Nginx или провайдер.

:::warning Правило значений по умолчанию в XMUX
Если блок `xmux` не задан (или все его поля равны `0`), Xray автоматически применяет три случайных диапазона: `maxConcurrency: "16-32"`, `hMaxRequestTimes: "600-900"` и `hMaxReusableSecs: "1800-3000"`. **Как только вы вручную укажете хотя бы одно поле, остальные значения по умолчанию сбрасываются в `0`**, поэтому их нужно прописать явно. Старый `mux.enabled: true` при работе с XHTTP включать нельзя.
:::

| Поле `xmux` | По умолчанию | Тип | Что делает и как настраивать |
| :--- | :--- | :--- | :--- |
| `maxConcurrency` | `"16-32"` | число / диапазон | Сколько одновременных прокси-запросов помещается в одно TCP/QUIC-соединение. Когда лимит достигнут, Xray открывает новое соединение. **Нельзя задавать вместе с `maxConnections`.** Для многопоточного теста скорости ставьте `1`. |
| `maxConnections` | `0` | число / диапазон | Максимум одновременных базовых соединений. Пока лимит не достигнут, каждый запрос открывает свой канал, затем каналы переиспользуются. Значение `1` заставляет весь трафик идти по одному соединению. |
| `cMaxReuseTimes` | `0` | число / диапазон | Сколько всего прокси-запросов может обслужить одно соединение за свою жизнь. После исчерпания лимита новые запросы в него не попадают, и оно плавно закрывается. |
| `hMaxRequestTimes` | `"600-900"` | число / диапазон | Лимит **HTTP-запросов** на одно соединение. Нужен, потому что Nginx по умолчанию закрывает соединение после 1000 запросов (`keepalive_requests`). В `packet-up` при достижении лимита очередной `POST` без разрыва переключится на новый канал. |
| `hMaxReusableSecs` | `"1800-3000"` | число / диапазон | Максимальный срок жизни TCP/QUIC-соединения в секундах (Nginx по умолчанию закрывает канал через 3600 с). |
| `hKeepAlivePeriod` | `0` | число (сек) | Период отправки :term[keepalive] в простаивающем соединении (`0` означает 45 с для H2 и 10 с для H3, `-1` отключает проверку). Единственное поле XMUX, где **запрещён диапазон** (случайный период сам по себе является признаком). |

## Разделение восходящего и нисходящего каналов (`downloadSettings`) {#uplink-downlink-split} :orig[~:上下行分离 | 上下行分离]

В режимах `packet-up` и `stream-up` сервер связывает отправку (uplink) и загрузку (downlink) только по случайному UUID в запросе. Благодаря этому клиент может отправлять данные **по одному маршруту**, а получать **по совершенно другому**:

- **Разные стеки и IP:** uplink идёт по `IPv4 + TCP + HTTP/2`, а downlink работает через `IPv6 + QUIC + HTTP/3`.
- **Разные SNI в одном CDN (:term[domain-fronting]):** uplink использует `serverName: "a.example.com"`, для downlink задаётся `"b.example.com"`, а общим `host` служит `"c.example.com"`.
- **Две независимые точки входа REALITY:** два разных сервера-моста пересылают трафик на один и тот же XHTTP-вход конечного сервера.

```jsonc
"downloadSettings": {
  "address": "downlink.example.com",
  "port": 443,
  "network": "xhttp",
  "security": "tls",
  "tlsSettings": {
    "serverName": "downlink.example.com",
    "alpn": ["h3"],
    "fingerprint": "chrome"
  },
  "xhttpSettings": {
    "host": "origin.example.com",
    "path": "/yourpath"
  }
}
```

- Объект `downloadSettings` (только на клиенте) представляет собой независимый `streamSettings` с дополнительными полями **`address`** и **`port`**.
- Поле `network` обязательно должно быть `"xhttp"`, а `path` должен совпадать с восходящим каналом.
- Настройки `xmux` и `tlsSettings`/`realitySettings` для uplink и downlink работают **полностью независимо** (даже случайные диапазоны XMUX выбираются раздельно, что разрушает корреляцию по времени переподключения).
- Единственное исключение: если на uplink задано `sockopt.penetrate: true`, системные опции сокета (например, `mark` для прозрачного прокси) наследуются и для downlink.

## Подробный справочник параметров `extra` и `config.proto` {#xhttp-extra-fields} :orig[xhttpProto: | splithttp/config.proto]

Все перечисленные ниже поля указываются внутри объекта `xhttpSettings.extra`. Почти для всех числовых параметров поддерживается либо точное число (`1000`), либо случайный диапазон строкой (`"100-1000"`).

### Буферизация, размеры и тайминги (`packet-up` / `stream-up`) {#xhttp-buffering}

| Параметр | Сторона | По умолчанию | Назначение |
| :--- | :---: | :---: | :--- |
| `scMaxEachPostBytes` | Клиент / Сервер | `1000000` (1 МБ) | Максимальный размер тела одного `POST`-запроса в режиме `packet-up`. Уменьшите (например, `"500000-1000000"`), если CDN или прокси режут крупные `POST`. |
| `scMinPostsIntervalMs` | Клиент | `30` мс | Минимальная пауза между последовательными `POST`-запросами в `packet-up`, чтобы не забить очередь на прокси или CDN. |
| `scMaxBufferedPosts` | Сервер | `30` | Сколько неупорядоченных `POST`-пакетов сервер хранит в буфере ожидания, если пакеты пришли не по порядку `seq`. |
| `scStreamUpServerSecs` | Сервер | `"20-80"` с | Через сколько секунд сервер в режиме `stream-up` завершает текущий потоковый `POST` (и клиент плавно открывает следующий). |
| `uplinkChunkSize` | Клиент | нет | Размер отдельного чанка при разбиении исходящего потока (полезно при кастомном размещении данных в заголовках/cookies). |
| `serverMaxHeaderBytes` | Сервер | нет | Максимально допустимый размер HTTP-заголовков, принимаемых сервером XHTTP. |

### Заголовки и совместимость с прокси / CDN {#xhttp-headers}

| Параметр | Сторона | По умолчанию | Назначение |
| :--- | :---: | :---: | :--- |
| `headers` | Клиент | `{}` | Словарь дополнительных HTTP-заголовков (`{"User-Agent": "..."}`). Поле `Host` задаётся только через `xhttpSettings.host`. |
| `noGRPCHeader` | Клиент | `false` | Отключает добавление заголовка `Content-Type: application/grpc` в режимах `stream-up` и `stream-one`. Оставьте `false`, если трафик идёт через Cloudflare или Nginx `grpc_pass`. |
| `noSSEHeader` | Сервер | `false` | Отключает ответный заголовок :term[sse] (`Content-Type: text/event-stream`). Обычно оставляют `false`, чтобы обратные прокси не буферизовали скачивание. |
| `uplinkHTTPMethod` | Клиент / Сервер | `"POST"` | Позволяет заменить HTTP-метод восходящего канала (например, на `PUT`) в нестандартных сетях. |
| `h2Params` | Клиент / Сервер | нет | Низкоуровневая настройка параметров HTTP/2-фреймов. |

### Гибкий паддинг (`xPadding*`) {#xhttp-padding}

Чтобы скрыть характерную длину запросов от :term[dpi], XHTTP добавляет к каждому запросу и ответу случайный :term[padding]:

| Параметр | По умолчанию | Назначение |
| :--- | :--- | :--- |
| `xPaddingBytes` | `"100-1000"` | Длина случайного паддинга в байтах (можно задать диапазон). |
| `xPaddingObfsMode` | `false` | Включает расширенный режим обфускации расположения и формата паддинга. |
| `xPaddingPlacement` | `queryInHeader` (`Referer`) | Куда помещать паддинг: в `Referer`, в `query`, в `header` или в `cookie`. |
| `xPaddingKey` | `"x_padding"` | Имя параметра/ключа, в котором передаётся строка паддинга. |
| `xPaddingHeader` | `"X-Padding"` | Имя HTTP-заголовка, если выбран режим передачи через заголовок. |
| `xPaddingMethod` | `"repeat-x"` | Способ генерации содержимого паддинга (`repeat-x`, случайные символы и т.д.). |

### Кастомное размещение метаданных (`sessionID*`, `seq*`, `uplinkData*`) {#xhttp-placement}

По умолчанию идентификатор сессии (`UUID`) и порядковый номер пакета (`seq`) передаются в URL-пути (`/yourpath/<uuid>/<seq>`). Если промежуточный фильтр или DPI начинает блокировать характерные длинные пути, метаданные можно перенести в заголовки, query-параметры или cookies (настройки должны совпадать на сервере и клиенте):

| Параметр | Назначение |
| :--- | :--- |
| `sessionIDPlacement` / `sessionIDKey` | Где передавать ID сессии (`path`, `query`, `header`, `cookie`) и имя ключа. |
| `sessionIDTable` / `sessionIDLength` | Алфавит символов и диапазон длины генерируемого идентификатора сессии. |
| `seqPlacement` / `seqKey` | Где передавать порядковый номер `POST`-пакета `seq` в `packet-up` и имя ключа. |
| `uplinkDataPlacement` / `uplinkDataKey` | Где передавать полезную нагрузку uplink (`body`, `header`, `cookie`, `query`) и имя ключа. |

## Пример настройки за Nginx {#xhttp-nginx} :orig[~:Nginx 推荐 grpc_pass | Nginx 反代配置]

Для режимов `stream-up` и `stream-one` (по умолчанию при `TLS H2`) официальная документация рекомендует проксировать XHTTP через `grpc_pass` — так Nginx не буферизует потоковые запросы:

```nginx
location /yourpath {
    grpc_pass grpc://127.0.0.1:20000;
    grpc_set_header Host $host;
    grpc_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    client_max_body_size 0;
}
```
